## 결론과 계산의 한계

자동 백업을 끄면 전송량이 크게 줄어든다. 그러나 기기 수와 실제 저장·조회 횟수가 없어 무료 월 5GB로 충분하다고 보장할 수 없다. 아래 기기 수별 표는 과거 데이터의 실제 JSON 크기를 사용한 **압축 전 보수적 시나리오**이며, Supabase 실측 사용량과 구분한다. 사용자가 제공한 Usage 화면에서는 이전 청구 주기 Egress 합계 **16.127GB**가 확인되었다. 실제 egress는 서버 계측, 압축, 요청 중복 합치기, 편집 중 조회 생략 등에 따라 달라진다. 관측하지 못한 신규 기능·반복 조회가 많으면 아래 수치보다 커질 수 있어 절대 상한도 아니다.

현재 Supabase 연결 도구에서 운영 프로젝트 조회가 거부되었다. 연결에서 보이는 프로젝트 목록에 운영 프로젝트가 없으므로 연결 도구를 통한 실제 조직 Usage, 정확한 기간별 서비스 비중, 현재 기록 증가량은 확인하지 못했다. 사용자가 제공한 대시보드 화면의 수치는 아래 별도로 반영했다. 연결 도구의 접근 범위는 여전히 확인이 필요하다.

- 무료 5GB 대비 3.23배이며, 같은 기간·사용 조건에서 5GB에 맞추려면 **약 69.0% 절감**이 필요하다.
- 월 4GB를 목표로 잡으면 **약 75.2% 절감**이 필요하다.

- 따라서 수정과 백업 중단이 69~75%를 실제로 절감하는지는 배포 후 같은 사용 조건의 일별 증가량으로 검증해야 한다. 현재 근무자동화 변경은 로컬이며 아직 배포되지 않았다.

## 코드에서 확인한 낭비와 수정

1. 근무자동화의 PT 인원 표시가 `pt_daily_records` 전체 변경 스트림을 구독하여, PT 날짜별 전체 기록을 수신하고 있었다. 날짜만 담긴 broadcast를 우선 사용하도록 바꾸고, 직접 DB 알림은 작은 설정/수동 인원 메타데이터에만 필터를 걸었다. 범위 밖 날짜와 프리셋 변경은 인원 재조회에서 제외하고, 연속 알림은 150ms 동안 합친다. 30초 주기 인원 조회와 화면 복귀·재연결 확인은 유지한다.
2. 충격파 경량 조회가 변경을 발견했을 때 관계없는 근무표 3개월도 재조회하던 부분을 제외했다.
3. 창 포커스·화면 복귀에 따른 강제 조회 최소 간격을 1.5초에서 30초로 늘렸다. 연결 복구를 위해 이미 예약한 조회를 포커스 제한이 취소하지 않도록 했다. 실시간 개별 셀 변경 반영은 유지한다.
4. 백업 자동 실행이나 기기별 설정은 변경하지 않았다. 아래 계산은 사용자가 모든 기기에서 자동 전체 백업과 실시간 백업 기록을 끈 경우를 가정한다. 실시간 백업 기록이 별도로 켜져 있으면 추가 수신이 남는다.

## 이전 백업 비용의 예

근무자동화 자동 전체 백업의 기본 설정 간격은 10분이며, 실제 각 기기의 설정 간격은 확인하지 못했다. 10분마다, 하루 8시간, 월 25일이면 48 × 25 = 1,200번 전체 조회한다.

`3,387,451 × 1,200 = 약 4.06GB/월/기기` (압축 전).

3대면 약 12.19GB, 5대면 약 20.32GB의 반복 전체 조회다. 실제 서버 계측 전송량과 동일한 수치라는 뜻은 아니다. PT 자동 백업은 별도이며 과거 전체 날짜 기록만으로 1회 약 6.34MB가 추가될 수 있다. 따라서 백업만으로도 상당한 원문 조회량이 발생했을 가능성이 있으나, 과거 전체 egress에서 차지한 비율은 확인하지 못했다.

## 두 앱에서 자동 백업을 껐을 때

### 사용 가정

- 각 기기에 두 앱을 모두 열어 둠. 월 25일, 하루 8시간.
- PT 저장 횟수는 **모든 기기의 합계**로 하루 100회 또는 300회. 환자 수가 아닌 저장 요청 횟수다.
- PT 저장 1회당 전체 기록 수신을 기기당 최대 3회(변경 행 실시간 수신, DB 알림 후 조회, broadcast 후 조회)와 작성 기기의 병합용 읽기 1회로 잡는다. 실제로는 요청 합치기·편집 중 생략으로 더 적을 수 있다.
- PT 전체 검색 이력을 기기당 하루 1회 6.31MB 읽는다고 가정한다. 실제 검색 기간이 짧거나 캐시가 있으면 더 작다.
- PT에는 v487 이후에도 별도의 공유 프리셋·열서식 조회가 남아 있다. 과거 설정 크기 20,153 + 5,283 + 194바이트와 날짜 revision 80바이트를 매 30초 모두 수신하는 보수적 경우를 반영했다. 프리셋 revision 캐시가 적중하면 실제는 줄어든다. 이 설정 조회량까지 0으로 계산하지 않았다.
- 근무자동화 일반 사용에는 과거 전체 테이블 JSON 크기의 하루 3배(약 10.16MB/기기)를 조회 예산으로 둔다. 이는 실제 측정값이 아니라 초기 로딩·검색·통계·인원 조회 등을 위한 명시적 가정이다. 대량 조회를 자주 하면 부족할 수 있다.
- 요청 헤더·인증·WebSocket 유지·로그·다른 프로그램 사용 등 실제 계측 비용은 별도이므로 무료 5GB 한계까지 모두 쓸 수 있다고 판단하지 않는다.

### 산식

`N_PT`: PT 기기 수, `N_ABS`: 근무자동화 기기 수, `C`: 하루 전체 PT 저장 횟수.

- PT 정기 설정/변경 확인: `25일 × N_PT × 960회 × 25,710바이트`
- PT 초기 검색 이력: `25일 × N_PT × 6,314,823바이트`
- PT 실제 변경/병합: `25일 × C × (3 × N_PT + 1) × 47,640바이트`
- 근무자동화 일반 조회 예산: `25일 × N_ABS × 3 × 3,387,451바이트`

### 기기 수별 시나리오

| 두 앱을 켜 둔 기기 수 | PT 합계 하루 100회 저장 | PT 합계 하루 300회 저장 |
|---|---:|---:|
| 1대씩 | 1.51GB | 2.46GB |
| 3대씩 | 4.28GB | 6.66GB |
| 5대씩 | 7.05GB | 10.86GB |
| 10대씩 | 13.98GB | 21.37GB |

무료 5GB와 비교하면 1대의 가정에서는 여유가 있을 수 있고, 3대부터는 사용량에 따라 경계 또는 초과가 가능하다. 5대 이상을 이 가정대로 사용하는 경우 무료로 충분하다고 안내할 수 없다. 이는 압축·요청 합치기의 절감 효과를 적용하지 않은 계산이며, 실제 기록 크기/저장 횟수로 다시 계산해야 한다.

## 실제 전환 전 확인

- Supabase의 운영 프로젝트가 보이는 계정과 연결 범위로 재연결한다.
- 운영 조직 Usage에서 Database/Realtime 등 egress 항목, 기간, 다른 프로젝트 사용량을 확인한다.
- 개선 버전 적용 및 백업 중단 후 3~7일의 일별 증가량을 확인한다. 하루 평균 × 실제 월 사용일로 추정하되 초기 이력 다운로드와 평일/휴일을 구분한다.
- 모든 기기에 개선 버전을 적용해야 계산 가정이 맞는다. 근무자동화 수정은 현재 로컬 코드이며 아직 배포되지 않았다. PT는 이미 배포된 v487 기준이다.
